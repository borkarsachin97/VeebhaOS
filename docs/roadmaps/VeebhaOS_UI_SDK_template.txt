CUSTOM FEATURE-PHONE OS: UI TEMPLATE ENGINE & SDK ROADMAP
THE THREE-TIER ARCHITECTURAL MODEL

The entire system is divided into three distinct layers:

Tier 1: Applications (Settings, SMS, Music Player, Contacts, Dialer)

Submits pure data structures (labels, arrays, icons).

Implements callback functions (on_select, on_back, on_action).

Completely unaware of pixel coordinates, screen dimensions, or LCD buses.

Tier 2: Shell & Template Runtime (The Middleware SDK)

Enforces strict screen viewport partitioning.

Auto-generates layouts using responsive flow and alignment rules.

Manages the screen history stack, memory allocation, and heap cleanup.

Routes D-pad focus, assigns softkey labels, and handles long-press gestures.

Tier 3: UI & Graphics Subsystem

LVGL v9 core engine (rendering, invalidation, styling, fonts).


Low-level hardware drivers (GOUDA DMA blitter, keypad matrix scanner).

CORE LOGIC OF THE "ZERO-COORDINATE" ENGINE

To eliminate manual coordinates, the middle layer enforces three rigid vertical zones across the 176x220 display:

Zone A: Fixed Top Header (Status Bar, ~18-20px)

Reserved exclusively for the system.

Displays persistent indicators: digital clock, battery percentage, Bluetooth status, network bars.

Applications cannot directly modify layout here; they only pass a title string that updates the header automatically.

Zone B: Elastic Viewport (~180-182px)

The active application work area where templates construct the UI.

All geometry is calculated using relational rules (proportional flex columns or relative grid cells) rather than absolute pixel offsets.

Elements automatically expand to fill available row width or equal fractions of column space.

Zone C: Fixed Bottom Footer (Softkey Bar, ~18-20px)

Dedicated to the Left Softkey (Action/Options) and Right Softkey (Back/Clear).

Applications define string labels for these keys.

The engine renders the text in high-contrast styling and routes physical button presses directly to the assigned callbacks.

THE 5 STANDARD TEMPLATE BLUEPRINTS

Every screen in the operating system can be created through one of five standard structural contracts:

Template 1: List View

Logical behavior: Receives an array of items (title text, optional icon, optional detail text or toggle switch).

Engine responsibility:

Instantiates a single vertical flex container that flows downward.

Enforces uniform row heights (typically 26-30px) for consistent scrolling ergonomics.

Enables center-locked vertical scrolling so the active item always remains visible in the middle of the viewport.

Registers every row automatically into the global D-pad navigation group.

Defaults the Right Softkey to the "Back" action.

Template 2: Matrix Grid View

Logical behavior: Receives an array of icon-and-title pairs (for example, a 9-icon launcher, photo gallery, or calculator).

Engine responsibility:

Divides the viewport into a uniform 3-column or 4-column grid.

Handles 4-way D-pad navigation across row boundaries (pressing Right at the end of Row 1 wraps naturally to the first item of Row 2).

Automatically centers and scales icons inside their grid cells.

Template 3: Modal Dialog

Logical behavior: Receives an alert type (Info, Warning, Confirmation), a message string, and confirmation/cancellation callbacks.

Engine responsibility:

Suspends input processing on the underlying screen without unloading it from memory.

Centers a dialog card in the viewport and applies an automatic background dimming mask.

Rebinds the softkeys dynamically (Left = Confirm, Right = Cancel).

Automatically closes and destroys itself once an action is selected.

Template 4: Form & Text Editor

Logical behavior: Receives a field prompt and a pointer to a text buffer (used for writing SMS, editing contacts, entering passwords).

Engine responsibility:

Generates single-line or multi-line text boxes.

Routes numeric keypad input directly into the multi-tap character engine.

Displays an input mode indicator in the top header (cycling through Abc, abc, 123).

Maps the Right Softkey to short-press Backspace and long-press Clear All.

Template 5: Media & Dashboard

Logical behavior: Receives media metadata (track title, artist, album art pointer, duration) or call status (contact name, call timer, call state).

Engine responsibility:

Arranges content into four fixed vertical slots: visual asset, primary title, secondary metadata, and progress/volume bar.

Rebinds D-pad Left and Right to seek or adjust volume without shifting UI focus away from the canvas.

NAVIGATION, STATE, AND MEMORY MANAGEMENT

The middle layer prevents memory leaks and avoids deep recursive function calls using a clean navigation stack:

The Screen History Stack (LIFO: Last-In, First-Out):

Push Action: When an app moves to a child screen, the engine records the current screen identifier, saves the index of the actively highlighted row, hides the active view, and allocates the child view.

Pop Action: When the user presses the Right Softkey (Back), the engine destroys the current child view, reclaims its heap memory, restores the parent view, and snaps D-pad focus back to the exact row index the user was on previously.

Home Reset: Pressing the physical End/Power key clears the entire history stack down to index zero, returning immediately to the main launcher screen.

THE GLOBAL INTERRUPTION & OVERLAY SYSTEM

Special hardware key gestures override standard application behavior without terminating running applications:

Quick Settings Panel (Hold Call Button for 600ms+):

The middle layer drops down a half-height overlay on top of the running app.

Contains quick toggles: Bluetooth on/off, backlight brightness slider, flashlight, and silent mode.

Temporarily captures D-pad focus. Dismissing it returns focus back to the underlying app without redrawing.

Multitasking App Switcher (Hold * Key):

Captures the active state of the current application and suspends its timers.

Opens a horizontal carousel card deck displaying icons and titles of all backgrounded applications.

Selecting a card restores that app to the active screen; pressing Close (Right Softkey) calls the app termination handler and frees its heap memory.

STEP-BY-STEP ENGINEERING ROADMAP

Phase 1: Viewport Partitioning & System Chrome

Define the root screen container with fixed heights for header, content, and footer.

Build the status bar service to periodically update battery level, Bluetooth state, and RTC time.

Build the softkey dispatch service to intercept physical LSK/RSK presses and trigger assigned callback pointers.

Phase 2: Core Template Engines

Build the List Template Engine: implement vertical flex stacking, uniform row sizing, and automatic scroll-centering.

Build the Grid Template Engine: implement 3-column and 4-column mathematical wrapping for 2D keypad navigation.

Build the Dialog Template Engine: implement modal stacking, background dimming, and temporary softkey hijacking.

Phase 3: Screen Navigation Stack & Memory Cleanup

Implement the LIFO navigation stack (push, pop, reset_to_home).

Wire automatic memory cleanup so that any view popped from the stack cleanly releases its objects from heap memory.

Implement position-memory logic so parent screens remember which row was focused when returning from sub-menus.

Phase 4: Keypad Routing & Text Input Middleware

Create an input mediator that separates directional navigation (D-pad) from text entry (12-key multi-tap).

Implement the multi-tap state machine with an internal timeout timer (~800ms) for character confirmation.

Expose an editor template that accepts raw string buffers and handles cursor movement automatically.

Phase 5: Overlays & Task Switcher

Implement long-press detection in the keypad scanning loop.

Build the Quick Settings overlay on the graphics engine top layer.

Build the task-switching card carousel to park and resume running app screens.

Phase 6: SDK Packaging & App Migration

Standardize the public interface header files (shell_list.h, shell_grid.h, shell_dialog.h, etc.).

Rewrite existing apps (Settings, Audio Player, SMS) as pure data declarations, eliminating all hardcoded coordinates from your codebase.
